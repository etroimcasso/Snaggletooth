# The 65816 CPU core

The 65816 is the SNES's main CPU — the processor at the heart of the 5A22, running the game's own
code. This is its instruction-set core: a cycle-stepped interpreter running over an abstract bus, so
it executes the same way on plain memory as it will on the full system bus once that lands.

The core is CPU-only. It has no memory of its own, no DMA, no timers — it reads and writes a 24-bit
address space you supply. Give it flat RAM and every address is a plain byte; give it the SNES
machine's mapped bus (a later component) and the same instructions drive real hardware.

The core decodes the load/store and register transfers — LDA/LDX/LDY, STA/STX/STY/STZ, the
register-to-register transfers, XBA and XCE — the arithmetic and logic family — ADC/SBC, CMP/CPX/CPY,
AND/ORA/EOR and BIT — and the read-modify-write, stack and flag family — INC/DEC and INX/INY/DEX/DEY,
ASL/LSR/ROL/ROR, TSB/TRB, the push and pull instructions (including PEA/PEI/PER), the flag set/clear
ops, REP/SEP, and NOP/WDM — across every addressing mode, with the width machinery those exercise. The
status table in the [README](../README.md) tracks the coverage.

## The bus

The core talks to memory through any type that satisfies the `SnesBus` concept — an 8-bit read, an
8-bit write, and a cycle that drives an address without a valid access:

```cpp
template <typename B>
concept SnesBus = requires(B bus, std::uint32_t address, std::uint8_t value,
                           CycleKind kind) {
  { bus.read(address, kind) } -> std::same_as<std::uint8_t>;
  bus.write(address, value, kind);
  bus.internal(address);
  bus.internal(address, kind);
};
```

The address is 24 bits (a full 16 MB); the data is 8 bits. The 65816 is an 8-bit-data machine — a
16-bit access is two sequential byte accesses, low byte then high — so the bus only ever moves one
byte at a time. A flat array is the simplest conforming bus:

```cpp
#include "snaggletooth/cpu/cpu65816.h"

#include <array>
#include <cstdint>
#include <memory>

struct FlatRam {
  std::unique_ptr<std::array<std::uint8_t, 0x1000000>> bytes =
      std::make_unique<std::array<std::uint8_t, 0x1000000>>();

  std::uint8_t read(std::uint32_t address, snaggletooth::CycleKind) const {
    return (*bytes)[address & 0xFFFFFF];
  }
  void write(std::uint32_t address, std::uint8_t value, snaggletooth::CycleKind) {
    (*bytes)[address & 0xFFFFFF] = value;
  }
  void internal(std::uint32_t) {}
  void internal(std::uint32_t, snaggletooth::CycleKind) {}

  // Loading memory is not the CPU driving the bus, so it takes no cycle kind.
  void poke(std::uint32_t address, std::uint8_t value) { (*bytes)[address & 0xFFFFFF] = value; }
};
```

Every cycle the core runs reaches the bus through exactly one of those calls. A cycle that touches
memory calls `read` or `write`; a cycle that does not still drives the address bus, and calls
`internal` with the address it drove. So a count of bus calls is a count of cycles.

`CycleKind` says what an access is for, which is what a real bus needs to price it and what the chip's
pins report:

| Kind | The access |
|---|---|
| `OpcodeFetch` | the instruction byte — both the program and data addresses are valid |
| `OperandFetch` | a byte of the instruction's operand — a program address |
| `DataRead` / `DataWrite` | an ordinary data access |
| `RmwRead` / `RmwWrite` | the read and the write-back of a read-modify-write, held under the memory lock |
| `RmwModify` | the cycle between them, where the value changes inside the chip — no address is valid, and the memory lock stays held |
| `RmwModifyWrite` | that same cycle in emulation mode, where the chip drives a write of the byte it just read |
| `VectorRead` | an interrupt vector pull |

`RmwModify` and `RmwModifyWrite` arrive through `internal(address, kind)` and `write` respectively, so a
bus that prices cycles sees the memory lock held across the whole read-modify-write.

A bus that treats all memory alike, as `FlatRam` does, can ignore the kind. A bus that maps hardware
uses it: the SNES charges 6, 8 or 12 master cycles depending on the region an access reaches.

The core issues *every* documented memory access, including the dummy reads some instructions perform
and discard. On flat RAM a dummy read has no consequence; on a bus whose reads have side effects — the
system's memory-mapped registers — issuing them is what makes the core correct.

## State

The whole CPU is one value struct. Snapshot it by copying, restore it by assignment:

```cpp
struct Cpu65816State {
  std::uint16_t pc = 0;   // program counter (within the program bank)
  std::uint16_t s = 0;    // stack pointer
  std::uint16_t a = 0;    // accumulator (A is the low byte, B the high byte)
  std::uint16_t x = 0;    // X index register
  std::uint16_t y = 0;    // Y index register
  std::uint16_t d = 0;    // direct-page register
  std::uint8_t p = 0;     // processor status
  std::uint8_t dbr = 0;   // data bank register
  std::uint8_t pbr = 0;   // program bank register
  bool e = false;         // emulation mode

  std::uint8_t ir = 0;       // the instruction being executed
  std::uint8_t tcu = 0;      // cycle index within it; 0 means the next cycle fetches
  std::uint32_t ea = 0;      // effective-address scratch
  std::uint16_t ptr = 0;     // indirect-pointer scratch
  std::uint16_t tmp = 0;     // data scratch (a low byte latched while the high pends)
  bool pageCross = false;    // an index addition carried past a page

  bool nmiPending = false;   // latched by a high-to-low edge on the NMI line
  bool irqLine = false;      // the IRQ line's current level

  CpuRunState run = CpuRunState::Running;
};
```

The registers above `ir` are the architectural ones a program can see. `ir` through `pageCross` are
how far into an instruction the core is: because they live in the same struct, a state copy taken
part-way through an instruction is a complete snapshot, and restoring it resumes on the same cycle.
There is no execution state anywhere else.

`p` is the packed status byte. Named masks read and write its flags:

| Mask | Bit | Flag |
|---|---|---|
| `kCpuFlagN` | `0x80` | negative (high bit of the result) |
| `kCpuFlagV` | `0x40` | signed overflow |
| `kCpuFlagM` | `0x20` | 8-bit accumulator/memory when set |
| `kCpuFlagX` | `0x10` | 8-bit index registers when set |
| `kCpuFlagD` | `0x08` | decimal mode |
| `kCpuFlagI` | `0x04` | interrupt disable |
| `kCpuFlagZ` | `0x02` | zero |
| `kCpuFlagC` | `0x01` | carry |

### Widths and modes

The 65816 sizes its data at run time rather than in the opcode. The `m` flag sizes the accumulator and
memory — 8-bit when set, 16-bit when clear — and the `x` flag sizes the X and Y index registers the
same way. The same opcode `A9` is an 8-bit `LDA #$nn` under `m = 1` and a 16-bit `LDA #$nnnn` under
`m = 0`; the register struct always holds 16 bits, and the width decides which halves are live. An
8-bit load leaves the accumulator's high byte (`B`) intact; an 8-bit index load clears the index high
byte.

The `e` flag is emulation mode, a separate bit that reproduces a 6502. While `e` is set, `m` and `x`
are forced set (everything is 8-bit), the stack is pinned to page one (`SH` reads `$01`), the index
high bytes read zero, and the direct page wraps within a page when the direct register's low byte is
zero. `XCE` exchanges `e` with the carry flag — the one instruction that changes the mode.

`dbr` and `pbr` are the data and program bank registers: the program counter is 16-bit and runs within
`pbr`, while data accesses form their 24-bit address from `dbr` (or from a pointer). The direct
register `d` is a 16-bit base the direct-page addressing modes add their offset to.

## Running instructions

Construct the CPU from a starting state and step it. `stepInstruction()` runs to the next instruction
boundary and returns how many cycles that took:

```cpp
FlatRam ram;
ram.poke(0x000200, 0xA9);  // LDA #$2A (8-bit accumulator)
ram.poke(0x000201, 0x2A);

snaggletooth::Cpu65816 cpu(
    snaggletooth::Cpu65816State{.pc = 0x0200, .p = snaggletooth::kCpuFlagM});
std::uint32_t cycles = cpu.stepInstruction(ram);

// cpu.state().a  == 0x002A
// cpu.state().pc == 0x0202
// cycles         == 2
```

The full surface:

```cpp
class Cpu65816 {
 public:
  Cpu65816() = default;
  explicit Cpu65816(Cpu65816State state);

  const Cpu65816State& state() const noexcept;   // read the current state
  void restore(Cpu65816State state) noexcept;    // replace it wholesale

  template <SnesBus B>
  void stepCycle(B& bus);                        // execute one chip cycle

  template <SnesBus B>
  std::uint32_t stepInstruction(B& bus);         // run to the next boundary

  bool atInstructionBoundary() const noexcept;   // between instructions?

  void setNmiLine(bool asserted) noexcept;       // the NMI pin
  void setIrqLine(bool asserted) noexcept;       // the IRQ pin

  static constexpr bool cycleStepped(std::uint8_t opcode) noexcept;
};
```

Time is external: the caller decides how much to run by accumulating cycles against whatever budget it
keeps. The core holds no wall clock and starts no threads.

`restore()` and the state copy are how you replay: capture a state, run, and restore to run again from
the same point — the interpreter is a pure function of `(state, bus)`.

### One cycle at a time

`stepCycle()` runs a single chip cycle. A machine that has to interleave with the CPU part-way through
an instruction — seizing the bus for a transfer, delivering an interrupt at an exact position, letting
a timer advance in step with execution — drives the core this way:

```cpp
FlatRam ram;
ram.poke(0x000200, 0xA9);  // LDA #$1234 (16-bit accumulator)
ram.poke(0x000201, 0x34);
ram.poke(0x000202, 0x12);

snaggletooth::Cpu65816 cpu(snaggletooth::Cpu65816State{.pc = 0x0200});
cpu.stepCycle(ram);   // the opcode fetch
cpu.stepCycle(ram);   // the low operand byte
// cpu.atInstructionBoundary() == false — the instruction is half-run
// cpu.state().tmp             == 0x0034
cpu.stepCycle(ram);   // the high operand byte, and the load
// cpu.atInstructionBoundary() == true
// cpu.state().a               == 0x1234
```

`atInstructionBoundary()` reports whether the core sits between instructions. Calling
`stepInstruction()` part-way through one finishes that instruction rather than starting another, so
the two calls mix freely.

`cycleStepped()` says whether an opcode runs on the cycle engine. The engine carries the implied,
accumulator, immediate, direct-page, absolute and long instructions; the rest execute whole, so
`stepInstruction()` runs them correctly while `stepCycle()` cannot take them a cycle at a time. Ask
before stepping cycle by cycle.

### The interrupt lines

`setNmiLine()` and `setIrqLine()` are the pins, driven by the machine around the core. NMI is
edge-sensitive: the falling edge latches `nmiPending`, which survives until it is serviced, so pulling
an already-asserted line low again queues nothing. IRQ is level-sensitive: the core samples whatever
the line currently says, so a source must hold it asserted until it is acknowledged.

```cpp
cpu.setNmiLine(true);   // an edge — cpu.state().nmiPending is now set
cpu.setIrqLine(true);   // a level — cpu.state().irqLine follows the line
cpu.setIrqLine(false);
```

## The cycle bar

Cycle counts match the documented per-instruction totals, which on the 65816 depend on the running
state rather than the opcode alone:

- A 16-bit accumulator or index access costs one cycle more than an 8-bit one, because it is a second
  byte over the 8-bit bus.
- A direct-page access costs one cycle more when the direct register's low byte is non-zero.
- An indexed read with 8-bit index registers costs one cycle more when the index addition crosses a
  page; with 16-bit index registers it always pays that cycle. Indexed *stores* always pay it.

A count is never a formula the core evaluates. It is how many cycles the instruction ran, so the rules
above describe the totals that fall out rather than the arithmetic that produces them.

For the instructions the cycle engine carries, the bar is the placement of each access *within* the
instruction as well as the total: which cycle drives which address, which cycles reach memory and
which only drive the address bus, and the exact cycle a mode change takes effect on. `REP` is the
sharp case — its status byte settles at the end of its last cycle, so that cycle still runs under the
widths the instruction started with. The whole-instruction path issues the same accesses in the same
order, but within one call, so a machine cannot interleave with it part-way through.

## Direct-page addressing

The direct page is a movable 256-byte window into bank zero: the `d` register holds its base and a
direct-page instruction carries one byte of offset, so `LDA $10` reads `d + $10`. Three modes share
that shape — `dp`, `dp,X` and `dp,Y` — and the indexed pair add an index register to the offset before
the access.

The sum stays within bank zero. Emulation mode narrows it further when the direct register is page
aligned: with `d`'s low byte zero the address wraps inside the direct page itself, so `d = $1200`, an
offset of `$20` and `X = $F0` reach `$001210` rather than `$001310`. With a non-zero low byte, or in
native mode, the same addition runs on into the next page.

```cpp
FlatRam ram;
ram.poke(0x000200, 0xB5);  // LDA $20,X
ram.poke(0x000201, 0x20);
ram.poke(0x001210, 0x7E);

snaggletooth::Cpu65816 cpu(snaggletooth::Cpu65816State{
    .pc = 0x0200,
    .s = 0x01FF,
    .x = 0x00F0,
    .d = 0x1200,
    .p = snaggletooth::kCpuFlagM | snaggletooth::kCpuFlagX,
    .e = true});
cpu.stepInstruction(ram);
// cpu.state().a == 0x7E — the indexed offset wrapped inside the direct page
```

### Where the cycles go

A direct-page instruction fetches its offset, then spends a cycle for each addition it has to make
before the address is ready, and finally reaches memory:

- the opcode fetch;
- the offset byte;
- one cycle when the direct register's low byte is non-zero;
- one cycle when the mode is indexed;
- the data access, one cycle per byte.

The two addition cycles reach no memory, and both drive the address the offset came from. An indexed
direct-page mode always pays its cycle — unlike the absolute indexed modes, where an 8-bit index pays
only when the addition crosses a page.

### Read-modify-write

`ASL`, `LSR`, `ROL`, `ROR`, `INC`, `DEC`, `TSB` and `TRB` read their operand, change it, and write it
back to the same address, holding the memory lock from the read through the write. Between the two is
a cycle that reaches no memory: the value changes inside the chip.

A 16-bit operation reads both bytes low first and writes them back **high byte first** — the reverse
of the order it read them in.

In emulation mode that middle cycle drives a write instead, carrying the byte just read, so an 8-bit
read-modify-write writes its address twice: the unmodified value, then the result. On flat memory the
first write is invisible; on a bus whose writes have side effects, both land.

```cpp
FlatRam ram;
ram.poke(0x000200, 0x06);  // ASL $10
ram.poke(0x000201, 0x10);
ram.poke(0x001210, 0x42);

snaggletooth::Cpu65816 cpu(snaggletooth::Cpu65816State{
    .pc = 0x0200,
    .d = 0x1200,
    .p = snaggletooth::kCpuFlagM | snaggletooth::kCpuFlagX});
const std::uint32_t cycles = cpu.stepInstruction(ram);
// cycles == 5, and ram now holds 0x84 at 0x001210
```

## Absolute and long addressing

Absolute addressing names a 16-bit address in the data bank: `LDA $1234` reads `DBR:$1234`. Long
addressing carries its own bank in a third operand byte, so `LDA $7E1234` reaches that address whatever
`dbr` holds. Both come in indexed forms — `abs,X`, `abs,Y` and `long,X` — which add an index register
to the address before the access.

The addition runs across the whole 24-bit address, so it carries into the bank rather than wrapping
inside it: with `dbr` zero, `LDA $FFFF,X` with `X = 1` reads `$010000`.

```cpp
FlatRam ram;
ram.poke(0x000200, 0xBD);  // LDA $FFFF,X
ram.poke(0x000201, 0xFF);
ram.poke(0x000202, 0xFF);
ram.poke(0x010000, 0x5A);

snaggletooth::Cpu65816 cpu(snaggletooth::Cpu65816State{
    .pc = 0x0200,
    .x = 0x0001,
    .p = snaggletooth::kCpuFlagM | snaggletooth::kCpuFlagX});
cpu.stepInstruction(ram);
// cpu.state().a == 0x005A — the index carried into bank one
```

### Where the cycles go

An absolute instruction fetches its address, spends a cycle on the indexing addition when it has to,
and reaches memory:

- the opcode fetch;
- two operand bytes, or three for a long address;
- one cycle for the indexing addition, under the rules below;
- the data access, one cycle per byte.

The indexing cycle is paid **every time** by a store, by a read-modify-write, and by anything running
with 16-bit index registers. A read with 8-bit index registers pays it only when the addition carries
out of the low byte — the one case where the high byte still has to change. The long modes never pay it
at all, because their index goes into a full 24-bit address where no page carry has to settle.

That cycle drives an address without a valid access, and the address it drives is the interesting part:
the bank and high byte of the un-indexed address with only the low byte of the index added. So
`LDA $12F8,X` with `X = $10` drives `$001208` on that cycle before reading `$001308` on the next — a
page below where it is going. A bus with side effects on reads sees nothing, because the cycle asserts
no valid address; a machine watching the address pins sees the intermediate value.

```cpp
FlatRam ram;
ram.poke(0x000200, 0xBD);  // LDA $12F8,X
ram.poke(0x000201, 0xF8);
ram.poke(0x000202, 0x12);
ram.poke(0x001308, 0x7F);

snaggletooth::Cpu65816 cpu(snaggletooth::Cpu65816State{
    .pc = 0x0200,
    .x = 0x0010,
    .p = snaggletooth::kCpuFlagM | snaggletooth::kCpuFlagX});
const std::uint32_t cycles = cpu.stepInstruction(ram);
// cycles == 5 — four, plus the cycle the page carry cost
// cpu.state().a == 0x007F
```

### Read-modify-write

`ASL`, `LSR`, `ROL`, `ROR`, `INC`, `DEC`, `TSB` and `TRB` take absolute and `abs,X` forms, and behave
exactly as their direct-page counterparts do: the memory lock is held from the read through the write,
the cycle between them reaches no memory, a 16-bit operation writes back high byte first, and in
emulation mode that middle cycle drives a write of the unmodified byte. The indexed form pays its
indexing cycle unconditionally, so `ASL $1200,X` costs seven cycles at 8 bits and nine at 16.

## Indirect and stack-relative addressing

Seven modes reach memory through an address held somewhere else. Five read a pointer out of the direct
page; two work from the stack pointer. All seven are accumulator modes — `ORA`, `AND`, `EOR`, `ADC`,
`STA`, `LDA`, `CMP` and `SBC`, and nothing else.

| Mode | Written | Where the address comes from |
|---|---|---|
| Direct indexed indirect | `LDA ($10,X)` | X is added to the direct-page offset, then a 16-bit pointer is read there; the data bank supplies the bank |
| Direct indirect indexed | `LDA ($10),Y` | a 16-bit pointer at the offset, plus the data bank, plus Y |
| Direct indirect | `LDA ($10)` | a 16-bit pointer at the offset, plus the data bank |
| Direct indirect long | `LDA [$10]` | a 24-bit pointer at the offset, naming its own bank |
| Direct indirect long indexed | `LDA [$10],Y` | that 24-bit pointer, plus Y |
| Stack relative | `LDA $04,S` | the stack pointer plus the offset, always in bank zero |
| Stack relative indirect indexed | `LDA ($04,S),Y` | a 16-bit pointer at that stack address, plus the data bank, plus Y |

The index is added to the whole 24-bit address the pointer names, so it carries into the next bank
rather than wrapping inside the one it started in:

```cpp
FlatRam ram;
ram.poke(0x000200, 0xB1);  // LDA ($10),Y
ram.poke(0x000201, 0x10);
ram.poke(0x000010, 0xFF);  // the pointer: $FFFF
ram.poke(0x000011, 0xFF);
ram.poke(0x020004, 0x7F);  // dbr $01, so $01FFFF + 5 lands in bank two

snaggletooth::Cpu65816 cpu(snaggletooth::Cpu65816State{
    .pc = 0x0200,
    .y = 0x0005,
    .p = snaggletooth::kCpuFlagM | snaggletooth::kCpuFlagX,
    .dbr = 0x01});
cpu.stepInstruction(ram);
// cpu.state().a == 0x007F
```

A stack-relative operand is different: its bank is always zero, and so is the bank of its second byte,
so a 16-bit operand based at `$00FFFF` reads its high byte from `$000000`.

### Where the cycles go

- the opcode fetch;
- the offset byte;
- one cycle if the direct register has a low byte — the same cycle plain direct-page addressing pays,
  and the stack-relative modes never pay because they do not use the direct register;
- one more cycle for `(dp,X)`, which adds X before it can read the pointer, or for either stack-relative
  mode, which adds the offset to the stack pointer;
- the pointer, one cycle per byte — two, or three for the long modes, or none at all for `sr,S`;
- one cycle for the indexing addition, under the rules below;
- the data access, one cycle per byte.

`(dp),Y` pays its indexing cycle on the same terms an indexed absolute address does: every time for a
store or with 16-bit index registers, and for a read with 8-bit index registers only when the addition
carries out of the low byte. `(sr,S),Y` pays it **every time**. The long indexed mode never pays it,
because its index goes into a full 24-bit address where no page carry has to settle.

The address that cycle drives differs between the two indexed modes. `(dp),Y` drives the pointer's bank
and high byte with only the low byte of the index added — the same partly-finished address the absolute
indexed modes drive. `(sr,S),Y` instead stays parked on the last byte of the pointer it just read.

```cpp
FlatRam ram;
ram.poke(0x000200, 0xB3);  // LDA ($04,S),Y
ram.poke(0x000201, 0x04);
ram.poke(0x0001F8, 0x34);  // the pointer at S+4, in bank zero
ram.poke(0x0001F9, 0x12);
ram.poke(0x011236, 0x7F);

snaggletooth::Cpu65816 cpu(snaggletooth::Cpu65816State{
    .pc = 0x0200,
    .s = 0x01F4,
    .y = 0x0002,
    .p = snaggletooth::kCpuFlagM | snaggletooth::kCpuFlagX,
    .dbr = 0x01});
const std::uint32_t cycles = cpu.stepInstruction(ram);
// cycles == 7 — the indexing cycle is unconditional here
// cpu.state().a == 0x007F
```

### Where a pointer wraps

A pointer read out of the direct page is two or three consecutive addresses, and where the second one
lands is not always the first plus one.

In native mode the rule is simple: direct-page addresses live in bank zero, so a pointer based at
`$00FFFF` reads its high byte from `$000000` rather than from bank one.

Emulation mode adds a case. With the direct register page-aligned, the offset and any index are added
to the low byte alone, so the address stays inside the direct page — `LDA ($B6,X)` with `D = $B200` and
`X = $F9` reads its pointer from `$00B2AF`, not `$00B3AF`. Stepping to the pointer's *next* byte is a
separate matter, and only the three modes the 6502 and 65C02 already had — `(dp,X)`, `(dp),Y` and
`(dp)` — keep it inside the page, and then only with the direct register at zero. So with `D = $0000`,
a pointer based at `$0000FF` reads its high byte from `$000000`; with `D = $B200`, a pointer based at
`$00B2FF` reads its high byte from `$00B300`.

The four modes the 65816 added — `[dp]`, `[dp],Y` and both stack-relative modes — never wrap inside a
page. A `[dp]` pointer based at `$0000FE` reads on through `$000100`, into the stack page:

```cpp
FlatRam ram;
ram.poke(0x000200, 0xA7);  // LDA [$FE]
ram.poke(0x000201, 0xFE);
ram.poke(0x0000FE, 0x34);
ram.poke(0x0000FF, 0x12);
ram.poke(0x000100, 0x7E);  // the bank byte, read out of the stack page
ram.poke(0x7E1234, 0x5A);

snaggletooth::Cpu65816 cpu(snaggletooth::Cpu65816State{
    .pc = 0x0200,
    .p = snaggletooth::kCpuFlagM | snaggletooth::kCpuFlagX,
    .e = true});
cpu.stepInstruction(ram);
// cpu.state().a == 0x005A
```

In emulation mode the stack pointer's high byte is always `$01`, so a stack-relative address starts in
page one whatever was written to the stack pointer — but an offset that carries out of the low byte
reaches the page above it, and the pointer read by `(sr,S),Y` steps the same way.

## Arithmetic, comparison and BIT

ADC and SBC add to and subtract from the accumulator at its width, with the carry flag as the carry-in
and carry-out; the negative, zero, overflow and carry flags all describe the result. SBC is the same
adder run against the ones-complement of the operand, so a set carry means "no borrow". CMP, CPX and
CPY subtract without a carry-in and without storing — only the negative, zero and carry flags move,
and the carry is set when the register is at or above the operand. AND, ORA and EOR combine the operand
into the accumulator; an 8-bit operation leaves the accumulator's high byte intact.

BIT is the one instruction whose flags depend on its addressing mode. Every form sets the zero flag
from the bitwise AND of the accumulator and the operand. The non-immediate forms additionally copy the
top two bits of the *operand* (not the AND) into the negative and overflow flags; the immediate form
(`BIT #`) sets only the zero flag and leaves negative and overflow alone.

```cpp
FlatRam ram;
ram.poke(0x000300, 0x18);  // CLC — clear carry so it is a clean add
ram.poke(0x000301, 0x69);  // ADC #$15
ram.poke(0x000302, 0x15);

snaggletooth::Cpu65816 cpu(
    snaggletooth::Cpu65816State{.pc = 0x0300, .a = 0x0027, .p = snaggletooth::kCpuFlagM});
cpu.stepInstruction(ram);  // CLC
cpu.stepInstruction(ram);  // ADC — 8-bit binary add
// cpu.state().a & 0xFF == 0x3C  (0x27 + 0x15)
```

### Decimal mode

When the decimal flag (`d`) is set, ADC and SBC work in binary-coded decimal: each nibble is one
decimal digit, adjusted on the fly. The same operands above with `d` set add as decimal — `0x27 + 0x15`
becomes `0x42`, not `0x3C`. The negative, zero and carry flags stay meaningful (the carry marks a result
outside `0`–`99` for an 8-bit accumulator, `0`–`9999` for a 16-bit one); the overflow flag has no defined
meaning for decimal arithmetic. Decimal mode costs no extra cycle. Only ADC and SBC honour the flag — the
comparisons and the increment/decrement instructions are always binary.

## Read-modify-write, stack and flags

The increment, decrement, shift and rotate instructions read a value, change it, and write it back at
the accumulator width (INX/INY/DEX/DEY use the index width). INC and DEC move the negative and zero
flags only; ASL, LSR, ROL and ROR also move the carry — ASL and ROL shift the top bit out into carry,
LSR and ROR shift the low bit out, and the rotates feed the old carry into the vacated bit. LSR (and a
ROR with the carry clear) always leaves the negative flag clear, since a zero enters the top bit. TSB
and TRB test memory against the accumulator with a bitwise AND, set the zero flag from that AND, and
write the memory back with the accumulator's one-bits set (TSB) or cleared (TRB); the accumulator is
unchanged.

The push and pull instructions move a register through the stack. A 16-bit push stores the high byte
first, so the stack is little-endian and a pull reads the low byte back first. `PHA`/`PHX`/`PHY` and
their pulls follow the accumulator or index width; `PHP`, `PHB`, `PHK` and `PHD` push the status,
data-bank, program-bank and direct registers; `PLA`, `PLX`, `PLY`, `PLB` and `PLD` set the negative and
zero flags from what they pull, while `PLP` replaces the whole status byte. `PEA` pushes a 16-bit
immediate, `PEI` pushes a word read from the direct page, and `PER` pushes an address relative to the
next instruction.

`REP` and `SEP` clear or set the status bits named by an immediate mask; `CLC`/`SEC`, `CLI`/`SEI`,
`CLD`/`SED` and `CLV` change one flag each. Narrowing the index registers to 8-bit — with `SEP #$10`,
`PLP`, or entering emulation — clears the high bytes of X and Y at once. `NOP` does nothing; `WDM` is a
two-byte reserved no-op that steps the program counter over its second byte without reading it.

```cpp
FlatRam ram;
ram.poke(0x000400, 0x18);  // CLC
ram.poke(0x000401, 0x2A);  // ROL A — shift the carry (now 0) into bit 0

snaggletooth::Cpu65816 cpu(snaggletooth::Cpu65816State{
    .pc = 0x0400, .a = 0x0080, .p = snaggletooth::kCpuFlagM});
cpu.stepInstruction(ram);  // CLC
cpu.stepInstruction(ram);  // ROL A: 0x80 -> 0x00, carry := old bit 7 (1)
// cpu.state().a & 0xFF == 0x00
// carry flag set, zero flag set
```

The stack lives in bank zero. In emulation mode it is pinned to page one: the 6502-original push and
pull instructions wrap the pointer within `$0100`–`$01FF`, while the 65816-additional stack
instructions (`PEA`/`PEI`/`PER`, `PHB`/`PHK`/`PHD`, `PLB`/`PLD`) let the pointer cross out of page one
during the access and then force its high byte back to `$01`. In native mode the stack is a full 16-bit
pointer with no such wrapping.

## Testing against the vectors

The core is checked per opcode against the SingleStepTests 65816 vectors — before/after machine-state
cases, one file per opcode per processor mode (`NN.n.json` native, `NN.e.json` emulated). The suite
asserts each case's final registers, the documented cycle count, and every memory cell the case
accounts for, and it proves no write landed at an address the case does not list — a stray write
cannot hide even though the 16 MB space is held sparsely.

The vectors are large, machine-generated reference data and are not vendored. Point the build at a
local checkout of the SingleStepTests 65816 `v1` directory:

```
cmake -B build -DSNAGGLETOOTH_65816_VECTORS=/path/to/65816/v1
cmake --build build
ctest --test-dir build
```

Without that path the vector cases register but skip, naming the variable in the skip reason — the
hand-derived width cross-checks still run. Two environment variables shape a run:

- `SNAGGLETOOTH_65816_CASE_CAP=N` — run at most `N` cases per file for a fast dev loop; the cap prints
  what it truncated. Leave it unset for a full run.
- `SNAGGLETOOTH_REQUIRE_65816_VECTORS=1` — turn a missing vector set into a failure instead of a skip,
  so an environment that means to run the oracle can never report green while exercising none of it.

## Gotchas

- **The bus is 8-bit.** Every access moves one byte; a 16-bit operation is two of them, and that
  second byte is where the width-dependent extra cycle comes from.
- **Widths are state, not opcode.** The same load opcode is 8-bit or 16-bit depending on the `m` (or
  `x`) flag. An 8-bit load preserves the register's high byte.
- **Emulation mode forces invariants every step.** With `e` set, the stack high byte is `$01` and the
  index high bytes are zero regardless of what an instruction does — the core reapplies this before
  each instruction, so a "dirty" high byte in a restored state is normalized.
- **The program counter wraps within its bank.** `pc` is 16-bit and `pbr` does not change on a fetch,
  so execution wraps at a bank boundary.
- **An indexed absolute instruction drives an address it never reads.** The indexing cycle puts the
  un-carried address on the bus. It asserts no valid access, so a bus that qualifies its decoding on
  the valid-address pins ignores it; a bus that decodes the address pins alone sees a phantom access.
